# Contributing to marsemu

Thanks for helping. Bug reports, support for new firmware versions and devices,
and better hardware models are all welcome.

## What never goes into the repository, an issue or a pull request

* **Firmware images**, or excerpts of them (disassembly listings, dumped
  tables, decompiled code). Refer to an image by device type, version and file
  name, e.g. `VNSE3-0/Control/151/151_control_VNSE3-0_ems_app_0151_0928_094421.bin`.
  `.gitignore` keeps `*.bin` and `/firmware` out.
* **Certificates and keys**, including ones a firmware uploads to the module.
* **A real device's identity**: MCU UID, MAC addresses, MQTT client IDs and
  topic IDs, serial numbers, Wi-Fi credentials. Logs from the emulator use its
  own made-up identity and are fine to share; logs from a real device need
  these removed first. `--at` already hides Wi-Fi passwords.

## Setup and tests

```bash
python -m venv .venv && . .venv/bin/activate
pip install -e '.[test]'
python -m pytest                     # unit tests, no firmware needed (CI runs these)
```

Changes to a CPU, peripheral or device model also need the firmware tests,
which boot real images:

```bash
MARSEMU_FIRMWARE=/path/to/firmware MARSEMU_ARCHIVE=/path/to/marstek-firmware-archiv/firmwares \
    python -m pytest -m firmware     # tens of minutes; tests without their images are skipped
```

`MARSEMU_FIRMWARE` is a directory of images laid out as
`<device type>/<version>/<file>.bin` (e.g. `HMA-1/V232/…bin`), `MARSEMU_ARCHIVE`
a firmware archive (Venus control and BMS images, CT00x). See
[Getting firmware](README.md#getting-firmware) for where the images come from.
Say in the pull request which images you ran.

One firmware test opens the [hmjs](https://github.com/tomquist/hmjs) demo in
a browser against an emulated Venus E 3.0. It runs when `HMJS_DEMO` points
at a built demo (`npm run build` in hmjs, then `hmjs/demo/dist`) and Node
can load Playwright.

`docs/STATUS.md` is generated by booting every image you have:

```bash
python tools/survey.py --seconds 60 FILES… > docs/STATUS.md
```

## Pull requests

* Keep a pull request to one change, and update the README where the change
  makes it wrong (a new option, device or limit).
* Describe how a model was derived (datasheet, observed firmware behaviour,
  measurement on a real device) and how confident it is, as the table
  "What is modelled, and how well" in the README does.
* By contributing you agree that your contribution is licensed under the
  project's license, [GPL-2.0-or-later](LICENSE).
